# WD-01.11 – Save/Load und Versionsschema

**Stand:** 2026-08-27  
**Status:** DECIDED  
**Voraussetzung:** WD-01.01 bis WD-01.10

## Grundentscheidung

Save/Load ist ein eigener, strikt validierter Datenpfad. Eine `.cm3d`-Datei wird niemals direkt in Three.js oder die UI geladen.

Verbindliche Ladefolge:

1. Datei/Quelle einlesen.
2. JSON syntaktisch parsen.
3. `format` prüfen.
4. `schemaVersion` prüfen.
5. gegen das zur Version gehörende Schema validieren.
6. falls nötig und unterstützt: deterministische Migration auf die aktuelle Schema-Version ausführen.
7. migriertes Ergebnis erneut vollständig validieren.
8. fachliche Querverweise und SceneGraph-Konsistenz prüfen.
9. erst danach den aktuellen Projektzustand atomar ersetzen.
10. Three.js-Runtime, Objektbaum, Inspector und weitere UI-Zustände aus dem validierten Datenmodell neu aufbauen.

Ein Fehler in einem dieser Schritte führt zu einem kontrollierten Ladeabbruch. Der zuvor geöffnete Projektzustand bleibt unverändert.

## Formatkennung

Jede CM3D-Projektdatei muss auf Top-Level enthalten:

```json
{
  "format": "CM3D_PROJECT",
  "schemaVersion": "0.1.0"
}
```

`format` identifiziert den Dateityp. `schemaVersion` identifiziert ausschließlich die Struktur des gespeicherten Datenmodells und ist unabhängig von der Programm-/App-Version.

## Versionsschema

`schemaVersion` verwendet Semantic-Versioning-artige drei Teile:

`MAJOR.MINOR.PATCH`

Für CM3D gelten folgende Regeln:

- **PATCH**: strukturell kompatible Korrekturen oder zusätzliche optionale Felder ohne Migrationserfordernis.
- **MINOR**: rückwärts migratable Schema-Erweiterung oder kontrollierte Strukturänderung; eine explizite Migration kann nötig sein.
- **MAJOR**: potentiell nicht automatisch kompatible Änderung am Datenmodell.

Die erste verbindliche Schema-Version lautet:

`0.1.0`

## Kompatibilitätsregel

Die Anwendung besitzt eine definierte Menge unterstützter Schema-Versionen.

Beim Laden gilt:

- aktuelle Schema-Version → direkt validieren und laden
- ältere unterstützte Version → validieren, migreren, erneut validieren, laden
- neuere unbekannte Version → nicht verändern und nicht als aktuelle Version interpretieren; kontrolliert mit Hinweis ablehnen
- beschädigte/ungültige Version → Ladeabbruch

CM3D darf niemals eine unbekannte neuere Datei „best effort“ umdeuten und anschließend überschreiben.

## Migrationen

Migrationen sind explizite, versionierte und deterministische Funktionen.

Beispiel:

```text
migrate_0_1_0_to_0_2_0(project)
```

Verbindliche Regeln:

1. Migrationen arbeiten ausschließlich auf serialisierbaren CM3D-Daten.
2. Keine Three.js-Objekte, DOM-Zustände oder Browserhandles innerhalb einer Migration.
3. Eine Migration darf keine bestehende `projectId`, `objectId`, `materialId` oder andere fachliche Identität ohne ausdrücklich dokumentierte Notwendigkeit neu erzeugen.
4. Migrationen laufen schrittweise von Version zu Version.
5. Nach jeder Migrationskette erfolgt eine vollständige Validierung gegen das Ziel-Schema.
6. Migrationen müssen reproduzierbar sein: gleiche Eingabe → gleiche fachliche Ausgabe.
7. Die Originaldatei wird durch bloßes Öffnen/Migrieren nicht automatisch überschrieben.

## Sichere Lade-Transaktion

Laden erfolgt in einen temporären Kandidatenzustand.

Der aktuell geöffnete Projektzustand wird erst ersetzt, wenn der Kandidat vollständig erfolgreich durchlaufen hat:

- Parsing
- Schema-Prüfung
- Migration
- Schema-Validierung
- fachliche Referenzvalidierung
- SceneGraph-Validierung
- Transform-/Material-/ID-Konsistenz

Dadurch gibt es keinen „halb geladenen“ Zustand.

## Fachliche Validierung

Neben JSON-Schema-/Strukturprüfung muss mindestens validiert werden:

- `format === "CM3D_PROJECT"`
- gültige `schemaVersion`
- gültige und eindeutige `projectId`
- eindeutige `objectId`s
- gültige `parentId`-Referenzen
- zyklusfreier SceneGraph
- gültige Transformwerte
- keine `NaN`/Infinity-Werte
- keine Nullskalierung
- gültige `materialId`-Referenzen
- eindeutige Material-IDs
- bekannte oder kontrolliert tolerierte Objekt- und Materialtypen
- keine referenzierten Objekte/Materialien, die nicht existieren

## Unbekannte Felder und `extensions`

Kernfelder werden strikt validiert. Der ausdrücklich vorgesehene `extensions`-Bereich darf zusätzliche Daten enthalten, solange sie den Kern nicht überschreiben oder semantisch widersprechen.

Unbekannte Kernfelder dürfen nicht stillschweigend als unterstützt gelten. Bei späteren Erweiterungen muss klar entschieden werden, ob ein Feld optional tolerierbar oder schema-relevant ist.

## Save-Regel

Speichern besteht logisch aus:

1. aktuellen fachlichen Projektzustand lesen,
2. Datenmodell vollständig validieren,
3. kanonisches serialisierbares Projektobjekt erzeugen,
4. `schemaVersion` der aktuell verwendeten Schreibversion setzen,
5. JSON serialisieren,
6. erst danach in den gewählten Speicher schreiben.

Ein ungültiger Runtime-Projektzustand darf nicht stillschweigend als gültige `.cm3d`-Datei geschrieben werden.

## Atomare Speicherstrategie

Wo die Plattform dies zulässt, soll Speichern atomar erfolgen: erst neue vollständige Daten erzeugen/schreiben, dann den bisherigen gültigen Stand ersetzen.

Im Browser gilt mindestens: erst vollständig serialisieren und validieren, dann IndexedDB-/Dateispeicher aktualisieren. Ein Fehler während Serialisierung oder Validierung darf den letzten gültigen Speicherstand nicht zerstören.

## Autosave / Recovery

Autosave ist nicht Bestandteil von WD-02, aber architektonisch vorbereitet.

Spätere Autosave-/Recovery-Stände müssen:

- dieselbe `.cm3d`-Logik und Schema-Validierung verwenden,
- separat vom explizit gespeicherten Projektstand geführt werden,
- niemals ein fachlich ungültiges Teilobjekt als Recovery-Wahrheit speichern.

## Öffnen einer neueren Datei

Ist `schemaVersion` neuer als die höchste unterstützte Version:

- Datei nicht automatisch migrieren oder verändern,
- kein Teil-Laden in den aktiven Projektzustand,
- Nutzer klar informieren, dass die Datei mit einer neueren CM3D-Schema-Version erstellt wurde,
- optional später Read-only-/Preview-Funktion separat definieren.

## Öffnen einer beschädigten Datei

Bei Syntax-, Schema- oder Referenzfehlern:

- Ladeabbruch,
- aktives Projekt unverändert lassen,
- Fehlerursache möglichst konkret melden,
- keine automatische „Reparatur“ mit erfundenen Daten durchführen.

Spätere Reparatur-/Recovery-Werkzeuge dürfen separat entwickelt werden, müssen aber nachvollziehbar und explizit sein.

## Save/Load und Runtime-Zustände

Nicht Teil des Projekt-Save/Load sind insbesondere:

- Selection-State
- Undo/Redo-History
- Hover
- offene Dialoge
- temporäre Gizmo-Zustände
- Three.js-UUIDs
- WebGL-/GPU-Ressourcen
- DOM-Zustände

Nach erfolgreichem Laden werden diese Runtime-/UI-Zustände kontrolliert neu initialisiert.

## WD-02/P0.1-Anwendung

WD-02 muss mindestens folgende Kette nachweisen:

1. neues Projekt mit `schemaVersion = 0.1.0` erzeugen,
2. Würfel mit stabiler `objectId` erstellen,
3. Transform ändern,
4. Projekt vor Save validieren,
5. Projekt speichern,
6. Browser neu laden,
7. gespeicherte Daten einlesen,
8. `format` und `schemaVersion` prüfen,
9. vollständig validieren,
10. Runtime aus dem Datenmodell neu aufbauen,
11. derselbe Würfel mit derselben ID und denselben fachlichen Daten ist vorhanden,
12. Selection und Undo/Redo-History sind bewusst leer/neuinitalisiert.

Zusätzliche Negativtests für WD-02:

- ungültiges JSON → kein Projektverlust
- falsches `format` → Ablehnung
- unbekannte neuere `schemaVersion` → Ablehnung
- fehlende Parent-/Materialreferenz → Ablehnung
- beschädigter Transform → Ablehnung

## Abnahmekriterium WD-01.11

WD-01.11 ist erfüllt, wenn CM3D einen klaren, atomaren Save/Load-Vertrag besitzt, bei dem:

- nur valide Projektdaten gespeichert werden,
- geladene Daten vor Runtime-Aufbau vollständig geprüft werden,
- unterstützte ältere Versionen explizit migriert werden können,
- unbekannte neuere oder beschädigte Dateien sicher abgelehnt werden,
- fachliche IDs und Daten über Save/Load erhalten bleiben,
- ein fehlerhafter Ladeversuch den aktuell geöffneten Projektzustand nicht beschädigt.
