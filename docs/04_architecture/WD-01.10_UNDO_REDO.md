# WD-01.10 – Undo/Redo-Grundprinzip

**Stand:** 2026-08-27  
**Status:** DECIDED  
**Voraussetzung:** WD-01.01 bis WD-01.09

## Grundentscheidung

Undo/Redo arbeitet auf der fachlichen CM3D-Datenebene. Änderungen werden als **Commands** beziehungsweise **Transactions** aufgezeichnet, die nachvollziehbar beschreiben, welche Projektdaten vor und nach einer Benutzeraktion gelten.

Nicht Bestandteil der Undo/Redo-History sind Three.js-Objekte, DOM-Zustände, Hover, offene Menüs, temporäre Gizmo-Handles, Render-Caches oder andere reine Runtime-/UI-Zustände.

## Command-Prinzip

Ein Command beschreibt genau eine fachlich zusammengehörige Änderung oder eine bewusst zusammengefasste Benutzeraktion.

Ein Command enthält mindestens:

- `commandId`
- `type`
- `label`
- betroffene fachliche IDs (`objectId`, `materialId` usw.)
- ausreichende Daten für Undo
- ausreichende Daten für Redo

Beispiele:

- Objekt erzeugen
- Objekt löschen
- Transform ändern
- Objekt umbenennen
- Reparenting
- Material zuweisen
- Materialeigenschaft ändern

## Keine Runtime-Snapshots

Es werden keine Snapshots von Three.js-Meshes oder DOM-Strukturen gespeichert. Nach Undo oder Redo wird zuerst das fachliche Datenmodell geändert; danach synchronisieren Runtime- und UI-Schicht ihre Darstellung daraus.

Damit bleibt die History unabhängig davon, ob Three.js-Objekte zwischenzeitlich neu aufgebaut wurden.

## Before-/After-State

Für WD-02 wird ein pragmatischer Hybrid festgelegt:

- einfache Property-Änderungen speichern `before` und `after`
- Erzeugen/Löschen speichern die notwendige fachliche Objektdefinition
- komplexere Operationen dürfen mehrere Teiländerungen als eine Transaction bündeln

Beispiel Transform-Command:

```json
{
  "type": "scene.transform.change",
  "objectId": "obj_...",
  "before": {
    "position": {"x": 0, "y": 0, "z": 0},
    "rotation": {"x": 0, "y": 0, "z": 0, "w": 1},
    "scale": {"x": 1, "y": 1, "z": 1},
    "pivot": {"x": 0, "y": 0, "z": 0}
  },
  "after": {
    "position": {"x": 2, "y": 0, "z": 0},
    "rotation": {"x": 0, "y": 0, "z": 0, "w": 1},
    "scale": {"x": 1, "y": 1, "z": 1},
    "pivot": {"x": 0, "y": 0, "z": 0}
  }
}
```

## Transaction-Prinzip

Mehrere technische Einzelschritte, die für den Benutzer eine Aktion darstellen, werden als genau ein Undo-Schritt behandelt.

Beispiele:

- Reparenting mit Parent-Wechsel + Order-Anpassung + lokalem Transform-Neuberechnen
- Gruppieren mehrerer Objekte
- Löschen eines Objekts mit abhängigen Referenzbereinigungen

Eine Transaction muss atomar sein: Entweder alle Teiländerungen gelten oder keine.

## Transform-Interaktion / Command-Merging

Ein kontinuierlicher Drag am Transform-Gizmo darf nicht hunderte Undo-Schritte erzeugen.

Verbindliche Regel:

- Beginn der Benutzerinteraktion: `before` erfassen
- während Drag: Live-Datenmodell aktualisieren, aber noch keinen endgültigen History-Eintrag erzeugen
- Ende der Interaktion: finalen `after`-Stand erfassen
- genau einen Command in die History schreiben

Numerische Feldänderungen dürfen entsprechend nach abgeschlossener Eingabe/Bestätigung als ein Command geschrieben werden.

## History-Struktur

Zur Laufzeit existieren mindestens:

- `undoStack`
- `redoStack`

Neue fachliche Änderung:

1. Command ausführen
2. Command auf `undoStack`
3. `redoStack` vollständig leeren

Undo:

1. obersten Command von `undoStack` nehmen
2. `undo()` ausführen
3. Command auf `redoStack`

Redo:

1. obersten Command von `redoStack` nehmen
2. `redo()` ausführen
3. Command zurück auf `undoStack`

## Selection-State

Selection-State aus WD-01.09 ist grundsätzlich kein fachlicher History-Bestandteil.

Eine Operation darf nach Undo/Redo eine sinnvolle Auswahl setzen, um die Bedienung konsistent zu halten, aber dies ist ein UI-Nebeneffekt und nicht die fachliche Wahrheit des Commands.

Beispiel: Undo nach „Würfel erzeugen“ entfernt den Würfel; Redo erzeugt denselben fachlichen Würfel mit derselben `objectId` erneut. Ob er danach automatisch ausgewählt wird, ist UI-Verhalten.

## Objektidentität bei Undo/Redo

Undo/Redo darf für dieselbe rückgängig gemachte/erneut ausgeführte Operation nicht stillschweigend neue fachliche IDs vergeben.

Beispiel:

- Objekt `obj_A` wird erstellt
- Undo entfernt `obj_A`
- Redo stellt exakt `obj_A` wieder her

Damit bleiben Referenzen innerhalb derselben History-Sequenz stabil.

## Validierung

Jeder Command muss vor Ausführung beziehungsweise beim Undo/Redo die für ihn relevanten Datenmodell-Invarianten beachten, insbesondere:

- existierende referenzierte IDs
- keine Parent-Zyklen
- gültige Transformwerte
- gültige Materialreferenzen
- keine doppelten IDs

Ein ungültiger Command darf das Projektmodell nicht teilweise verändern.

## History und Save/Load

Für WD-02 wird die Undo/Redo-History **nicht** in der `.cm3d`-Projektdatei persistiert.

Nach Save → Browser-Reload → Load beginnt die Runtime-History leer. Gespeichert wird nur der aktuelle fachliche Projektzustand.

Eine spätere Session-Wiederherstellung oder persistente History wäre ein eigener Ausbau und darf nicht mit dem Projektformat vermischt werden.

## History-Limit

WD-02 verwendet ein konfigurierbares begrenztes History-Limit, damit Speicherverbrauch kontrolliert bleibt. Als Startwert wird **100 fachliche Commands/Transactions** vorgesehen.

Das Limit ist Runtime-/Anwendungskonfiguration und kein Bestandteil des fachlichen Projektdatenmodells.

## WD-02/P0.1-Anwendung

WD-02 muss mindestens nachweisen:

1. Würfel erzeugen → Undo entfernt ihn → Redo stellt dieselbe `objectId` wieder her.
2. Transform ändern → Undo stellt den exakten vorherigen fachlichen Transform wieder her → Redo den neuen.
3. kontinuierlicher Gizmo-Drag erzeugt genau einen Undo-Schritt.
4. Save/Reload/Load lädt den aktuellen Projektzustand, aber nicht die alte Undo-History.
5. Three.js-Objekte dürfen nach Undo/Redo aus dem fachlichen Modell neu synchronisiert werden.

## Abnahmekriterium WD-01.10

WD-01.10 ist erfüllt, wenn alle WD-02-relevanten Datenmodelländerungen als reproduzierbare Commands/Transactions mit stabilem Undo/Redo beschrieben werden können, ohne Three.js-, DOM- oder sonstige Runtime-Snapshots in der History speichern zu müssen.
