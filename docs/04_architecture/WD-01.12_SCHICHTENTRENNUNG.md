# WD-01.12 – Trennung Datenmodell ↔ Three.js ↔ Benutzeroberfläche

**Stand:** 2026-08-27  
**Status:** DECIDED  
**Voraussetzung:** WD-01.01 bis WD-01.11

## Grundentscheidung

CM3D wird in klar getrennte fachliche Schichten aufgebaut. Keine Schicht darf eine andere Schicht als versteckte Datenhaltung missbrauchen.

Verbindliche Reihenfolge der fachlichen Wahrheit:

1. **Datenmodell** – persistierbare Projekt- und Szenendaten
2. **Application/Service/Command-Schicht** – validierte fachliche Änderungen am Datenmodell
3. **Three.js-Runtime** – aus dem Datenmodell erzeugte 3D-Darstellung und Interaktionshilfe
4. **UI-Schicht** – Anzeige, Bedienung und Auslösen fachlicher Aktionen

Die `.cm3d`-Datenstruktur bleibt die kanonische Projektwahrheit.

## Datenmodell

Das Datenmodell enthält ausschließlich fachliche, persistierbare Projektdaten und deren gültige Beziehungen.

Dazu gehören insbesondere:

- Project-Metadaten
- Settings
- SceneObjects und `objectId`s
- Parent-Beziehungen und Reihenfolge
- Transformdaten
- Materialdefinitionen und `materialId`s
- Asset-Referenzen
- fachliche Flags und Extensions

Das Datenmodell kennt keine DOM-Elemente, keine Three.js-Objektinstanzen, keine WebGL-Ressourcen und keinen Browser-spezifischen UI-Zustand.

## Application-/Service-/Command-Schicht

Fachliche Änderungen werden nicht direkt aus UI-Komponenten oder Three.js-Helfern in beliebige Datenstrukturen geschrieben.

Stattdessen laufen Änderungen über klar definierte Aktionen/Services/Commands, zum Beispiel:

- `createObject(...)`
- `deleteObject(...)`
- `setTransform(...)`
- `reparentObject(...)`
- `assignMaterial(...)`
- `renameObject(...)`
- `saveProject(...)`
- `loadProject(...)`

Diese Schicht ist zuständig für:

- Validierung
- Einhaltung der Invarianten aus WD-01
- Undo/Redo-Integration
- atomare Transactions
- Aktualisierung des fachlichen Datenmodells
- Ausgabe klarer Änderungsereignisse für Runtime und UI

## Three.js-Schicht

Three.js ist Rendering- und Interaktions-Runtime, nicht Projektwahrheit.

Three.js darf:

- Meshes, Groups, Cameras und Lights aus CM3D-Daten erzeugen
- Weltmatrizen berechnen
- Raycasts durchführen
- Transform-Gizmos darstellen
- GPU-Ressourcen verwalten
- temporäre Caches führen

Three.js darf nicht:

- fachliche IDs festlegen
- eigene UUIDs als CM3D-Identität verwenden
- alleinige Quelle für Save/Load sein
- persistierbare Material- oder Transformdaten ausschließlich in Runtime-Objekten halten
- eigenständig fachliche SceneGraph-Regeln umgehen

Für jedes relevante Runtime-Objekt muss ein Mapping zur CM3D-`objectId` existieren.

## UI-Schicht

Die UI zeigt den aktuellen fachlichen Zustand und Runtime-/Selection-Zustände an und löst Benutzeraktionen aus.

Die UI darf:

- Objektbaum anzeigen
- Inspector-Werte anzeigen/bearbeiten
- Selection-State verwalten
- Commands auslösen
- Fehler/Validierungsergebnisse darstellen
- WORLD-/LOCAL-Werkzeugmodi steuern

Die UI darf nicht:

- versteckte zweite SceneObject-Datenbestände führen
- Persistenz direkt aus DOM-Zuständen erzeugen
- Three.js-Objekte direkt als langfristige Datenwahrheit verändern, ohne das Datenmodell zu aktualisieren
- eigene Objektidentitäten neben `objectId` erfinden

## Verbindlicher Datenfluss

### Benutzer ändert einen Transformwert im Inspector

1. UI liest `objectId` und neue Eingabe.
2. UI löst `setTransform(objectId, ...)` aus.
3. Command/Service validiert und schreibt den neuen lokalen Transform ins Datenmodell.
4. Undo/Redo erhält den fachlichen Command/Transaction-Eintrag.
5. Runtime erhält die Änderung und aktualisiert das zugehörige Three.js-Objekt.
6. UI liest/zeigt den bestätigten Zustand erneut aus der zentralen Quelle.

### Benutzer verschiebt ein Objekt mit dem Gizmo

1. Three.js/Gizmo ermittelt eine temporäre Transformänderung.
2. Runtime übersetzt das Ergebnis auf die zugehörige `objectId`.
3. Beim Commit der Aktion wird ein fachlicher Transform-Command ausgelöst.
4. Das Datenmodell wird validiert geändert.
5. Runtime und UI synchronisieren sich auf den bestätigten Modellstand.

Der Gizmo-Drag selbst darf nicht dazu führen, dass Three.js dauerhaft vor dem Datenmodell als Wahrheit davonläuft.

## Synchronisationsprinzip

Nach jeder bestätigten fachlichen Änderung gilt:

**Datenmodell zuerst, Runtime/UI daraus aktualisieren.**

Optimistische Vorschau während Drag/Interaktion ist erlaubt, muss aber beim Commit gegen den fachlichen Datenzustand synchronisiert werden.

Bei Fehlern oder abgelehnten Änderungen muss die Runtime auf den letzten gültigen Modellzustand zurückgesetzt werden können.

## Event-/Benachrichtigungsprinzip

Zwischen den Schichten dürfen Ereignisse verwendet werden, zum Beispiel:

- `objectCreated`
- `objectDeleted`
- `objectChanged`
- `sceneGraphChanged`
- `materialChanged`
- `projectLoaded`
- `selectionChanged`

Diese Events transportieren IDs und fachlich notwendige Änderungsinformationen, aber keine versteckten zweiten Projektzustände.

## Selection-State

Selection bleibt gemäß WD-01.09 Runtime-/UI-State. Er referenziert ausschließlich `objectId`s und ist nicht Teil der fachlichen `.cm3d`-Persistenz.

## Save/Load

### Save

Save serialisiert ausschließlich das validierte Datenmodell.

Nicht serialisiert werden:

- Three.js-Instanzen
- DOM
- Selection
- Undo/Redo-History
- temporäre Gizmo-/Hover-Zustände
- GPU-/Render-Caches

### Load

Nach erfolgreicher Validierung/Migration gemäß WD-01.11 wird das Datenmodell eingesetzt. Anschließend werden Runtime und UI vollständig daraus aufgebaut.

Three.js darf deshalb jederzeit komplett verworfen und neu erzeugt werden, ohne dass fachliche Projektdaten verloren gehen.

## Erlaubte Abhängigkeiten

Verbindlich erlaubt:

```text
UI -> Application/Commands -> Data Model
Three.js Runtime -> liest Data Model / reagiert auf Änderungen
Application/Commands -> benachrichtigt Runtime und UI
Save/Load -> Data Model
```

Nicht erlaubt:

```text
Data Model -> DOM
Data Model -> Three.js-Instanzen
Save/Load -> Three.js als Quelle
UI -> direkte dauerhafte Mutation von Three.js ohne Command/Model-Update
Three.js -> direkte fachliche Persistenz
```

## Projektstruktur-Folge für WD-02

Der spätere Code soll diese Trennung auch in der Verzeichnisstruktur widerspiegeln, mindestens logisch in Bereiche wie:

```text
src/
  model/
  application/
  persistence/
  runtime-three/
  ui/
```

Die endgültige Framework-/Build-Struktur wird erst beim WD-02-Setup konkret umgesetzt; die Schichtgrenzen sind bereits verbindlich.

## Testbarkeit

Ein zentrales Ziel dieser Trennung ist, dass wesentliche CM3D-Logik ohne WebGL getestet werden kann.

Mindestens folgende Dinge müssen ohne Three.js-Rendering testbar sein:

- Projektvalidierung
- SceneGraph
- IDs
- Parent-/Child-Regeln
- Transformdaten
- Einheitensystem
- Materialreferenzen
- Commands/Undo/Redo
- Save/Load und Migration

Three.js-spezifische Tests prüfen anschließend nur noch die korrekte Runtime-Abbildung dieser Daten.

## WD-02/P0.1-Anwendung

Für den ersten End-to-End-Prototyp gilt damit zwingend:

1. Würfel wird als CM3D-SceneObject erzeugt.
2. Runtime erzeugt daraus das Three.js-Mesh.
3. Objektbaum zeigt dasselbe SceneObject über `objectId`.
4. Auswahl referenziert dieselbe `objectId`.
5. Inspectoränderungen laufen über Commands ins Datenmodell.
6. Runtime wird aus dem bestätigten Modell aktualisiert.
7. Save serialisiert das Datenmodell.
8. Nach Reload/Load wird das Three.js-Mesh vollständig neu aus denselben CM3D-Daten erzeugt.

## Abnahmekriterium WD-01.12

WD-01.12 ist erfüllt, wenn für jede WD-02-Kernaktion eindeutig beantwortet werden kann:

- welche Schicht die fachliche Wahrheit besitzt,
- welche Schicht die Änderung validiert,
- welche Schicht rendert,
- welche Schicht nur UI-Zustand hält,
- was gespeichert wird und was nicht,

ohne zyklische oder versteckte Datenabhängigkeiten zwischen Datenmodell, Three.js und UI.

## Ergebnis WD-01

Mit WD-01.12 sind die zwölf Architekturpunkte von WD-01 vollständig entschieden.

Der nächste Schritt ist ein kurzer WD-01-Gesamt-Cross-Check auf Widersprüche und fehlende Übergänge zwischen WD-01.01 bis WD-01.12. Erst wenn dieser sauber ist, wird WD-01 abgeschlossen und WD-02/P0.1 begonnen.
